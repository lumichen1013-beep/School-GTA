1. 設計支柱、目標玩家、時長

1.1 設計支柱（可用來否決提案）

# 支柱 檢查方式
P1 兩種視角缺一不可：每個謎題都必須同時用到 3D 與 2D 能力，只用一種視角必定解不開 每個謎題至少一條「只用單一模式」的反例測試
P2 一章一個頓悟：每章的核心 aha 推翻或延伸前一章建立的直覺（不是換座標） 第 5 節表格「本章 aha」欄不得重複
P3 輕鬆的推理而非手速：無計時、無敵人、無精準跳躍要求；失敗成本只有走回去 不出現計時器；跳躍高度餘裕 ≥ 0.15（D10）
P4 物件會說話：可互動 / 只在某視角存在 / 可蓋印 等狀態一律有形狀符號，不只靠顏色 第 7 節無障礙檢查表
P5 在遊戲裡修遊戲：機制都以遊戲開發語彙命名（畫筆工具、提交、剖面檢視、標記點；顯示名見 story-bible 對照表），劇情與機制同源 新機制命名須通過此檢查

1.2 目標玩家

  • 國中到高中的青少年；喜歡 Monument Valley、Portal 一類「短而有頓悟」作品，不要求平台跳躍技術。
  • 文案短、直白、有一點幽默（劇情：遊戲社的你被吸進社團做到一半的遊戲，見 story-bible-v0.1.md）；鍵盤操作（WASD / Space / F·Q / E / T / R，見 puzzle.html）。

1.3 時長估計〔推論〕

項目 估計
主線總時長 約 4～5.5 小時（50 個主線謎題，各章題均 3.5～8 分；計算見 5.2）

3. 謎題設計原則（可檢查的規則）

# 規則 依據 怎麼檢查
D1 每個謎題最多一個新概念；新概念先在「無失敗風險」的小場景出現一次（教），下一題要求主動使用（測），再下一題換條件（變） 〔來源〕Portal 開發者評論：每個概念都刻意介紹與訓練；任天堂四段式（導入→發展→轉折→收束）〔來源，二手分析〕 第 6 節每題新概念 ≤ 1（同一關可依序教多個，如 1-1）
D2 每個謎題必須同時用到 2D 與 3D（支柱 P1） 本作核心 每題至少兩條反例測試：只用 3D、只用 2D
D3 頓悟必須推翻一個合理的錯誤假設；在謎題說明中寫出「玩家最可能的錯誤嘗試」 〔來源〕Blow：刪掉沒有驚喜或彼此重疊的謎題；〔推論〕把錯誤嘗試寫進規格才能確認驚喜存在 第 6 節每題有「錯誤嘗試」欄
D4 不得有跳過關鍵步驟的捷徑，以邏輯層測試證明（取樣木箱位置 × 切換點的反例迴圈，比照玄關 for z of [...] 寫法） 現有測試慣例 C17 每關反例測試至少覆蓋「關鍵物件在別處」的取樣
D5 不放純粹的紅鯡魚；允許「誘導性錯誤」——看起來可行、試了會學到東西（如玩家站壓板「太輕」） 〔查不到〕密室社群對紅鯡魚的系統性論述未找到可信來源；〔推論〕浪費時間的假線索會破壞玩家對謎題的信任，對青少年玩家尤其容易直接放棄 每個非必要物件需寫出它教了什麼或屬於哪個隱藏要素
D6 規則一致、不臨時例外：同外觀 = 同規則（Blow 讓所有不受倒帶影響的物件都發綠光）；新規則用新外觀 〔來源〕Blow IndieCade 報導 機制庫每項都有專屬外觀符號
D7 提示分三級且三級都抽象（意象 → 觀察角度 → 缺的性質），不給動作、不點名物件、不給數字（量表見 7.1.1）；把玩家推回邏輯路徑、不給答案；同一級提示被超過 50% 玩家使用 → 謎題要重做；L4 解法筆記被 ≥ 20% 打開 → 重做 〔來源〕Room Escape Artist 的提示文章 本機統計（第 8 節 puzzle:stats）＋ 驗證器（7.1.1）
D8 錯誤可逆：任何狀態都能以 T（木箱歸位）、R（重來）或回檢查點復原；不可能進入無解狀態而不自知 現有 C12、C13 每個新機制需寫「死局如何復原」
D9 整合章只允許用已教過的機制；筆桿機制（第四次升級）在地下室末段 4-3 教、閣樓首關 5-1 測試 / 變奏，之後 Boss 與終章才整合使用 〔來源〕Braid / The Witness 先把元素教完，之後難題只在探索已知機制的後果（Blow 相關報導） 第 5 節第五章「新概念」欄為「—」；6.9 教學順序自檢
D10 不靠精準操作：所有跳躍至少留 0.15 高度餘裕、0.3 水平餘裕；互動一律站穩 支柱 P3、現有 C9 數值寫進關卡註解並有測試

《圖紙之間》劇情設定 Story Bible v0.1

《圖紙之間》劇情設定 Story Bible v0.1　（此文件內無修訂紀錄）

用途：取代 game-spec-v0.2.md 原本的「建築師沈歸 / 宅邸 / 製圖員」劇情。 不變的部分：50 題 / 22 關 / 隱藏房 3、關卡 ID、N 機制編號、解法大綱，一律以規格為準。本文件只管敘事、命名、文案。 目標讀者：國中到高中的玩家。原則：一句話就懂，不寫隱喻與哲思。

1. 世界觀

1.1 一句話

遊戲社的你和社長，被吸進社團做到一半的密室逃脫遊戲《圖紙之間》，得把每個房間修好、讓遊戲能從頭玩到尾，才能回到社辦。

1.2 設定細節

問題 答案（給玩家的說法）
《圖紙之間》是什麼？ 遊戲社準備在校慶發表會展出的作品：在一棟老房子裡逃脫的解謎遊戲。目前只做到一半。
怎麼進去的？ 發表會前一週，社長在社辦按下「測試執行」，螢幕一白，兩個人就站在遊戲的門廊裡了。不解釋原理，一句帶過。
怎麼出去？ 遊戲必須能「從開頭玩到結尾」，最後一個畫面的「回到桌面」才會出現。所以每個房間都要修到能通關。
為什麼能切換 2D / 3D？ 社長做了一個除錯用的「切換檢視」鍵，用來對照「設計稿」（2D 平面圖）和「完成版」（3D 實際做出來的樣子）。被吸進來時，這個鍵跟著你，變成手上的畫筆。
為什麼兩邊不一樣？ 因為遊戲沒做完：有些東西畫進了設計稿但還沒做出來（只在 2D），有些東西做出來了卻忘了補進設計稿（只在 3D）。設計稿是一張平面的圖，所以沒有前後深度。
為什麼設計稿裡跳得比較高？ 設計稿的重力參數還是預設值，比較輕。（社長：「我之後會調……」）
為什麼是密室逃脫？ 遊戲本來就是密室逃脫。每個房間的門，就是那一關的「通關判定」。
為什麼要一關一關修？ 每一章是遊戲裡一個沒做完的模組（見 1.3）。前一個模組沒修好，下一個不會載入。
掉進坑會怎樣？ 掉出地圖，被傳回最近的檢查點。不會死，也不會受傷。
為什麼中途不能存檔？（規格 Q4 關內不存檔） 存檔系統只做了「過關時存檔」。社長：「中途存檔……下一版一定做！」所以每個房間要一口氣修完，按 R 是「重新載入這個房間」。
為什麼提示要等？（規格 7.1 計時解鎖） 提示是 AI 小助手「小格」在算，而且社長給它定了規矩：只能給方向、不能直接說答案。小格跑在遊戲剩下的一點記憶體上，所以每一級提示都要「運算」一段時間。小格發現你很努力（一直重置物件、一直切換），會把你的提示排到前面先算（卡關偵測）。設定裡的「提示隨時可用」= 社長幫你開了「開發者模式」。

1.3 章節 = 沒做完的模組

章 房間 遊戲裡的模組 這章要修的東西
第一章 門廊 / 玄關 / 衣帽間 教學模組 門、開關、最基本的切換
第二章 書房 物理模組（重量） 壓力板的重量、物件「提交」
第三章 溫室 光影模組 影子意外有了碰撞箱（bug 變成路）
第四章 地下室 社長的「封存」資料夾 被刪掉一半的功能：剖面檢視、標記點
第五章 閣樓 最終關（自動生成器） 一直重生、還沒定案的最終關

2. 角色

玩家稱呼一律用「你」；系統文字用玩家暱稱（開始時輸入，預設「新社員」）。不使用「他 / 她」指稱玩家。

2.1 你（玩家）

  • 身分：遊戲社今年的新社員，負責關卡設計。
  • 性格：由玩家決定；文案裡的「你」話不多、動手比較快。
  • 在故事裡的功能：拿著畫筆修 bug 的人。社長出點子，小格給提示，你把它做完。

2.2 社長：江若晴（大家叫「社長」或「若晴」）

  • 高二，遊戲社社長兼企劃兼美術兼「什麼都說好」。
  • 性格：開朗、點子很多、很會鼓勵人；缺點是常常開了頭就跑去做下一個點子，留下一堆「之後再改」。真心希望大家的作品被看見。
  • 口頭禪：「沒問題，明天就做完！」
  • 代表台詞：「我做的都只有一半……可是有你在，另一半好像就做得完了。」
  • 在故事裡的功能：每章開場與機制取得時說話；不負責給提示（避免和小格重疊）。

2.3 AI 小助手：小格

  • 社長很久以前做的教學 NPC，外型是一個方塊頭、會飄的小格子。做到一半被擱著，所以說話偶爾卡頓。
  • 性格：認真、講話像說明書、會吐槽社長；對你很有耐心。
  • 口頭禪：「運算中……」
  • 代表台詞：「提示運算完成。你其實已經想到一半了，我只是幫你按下確認。」
  • 提示系統的化身（對應規格 7.1 三級提示，三級全抽象）：小格只給「想的方向」，從不說要按什麼、推什麼、站哪裡。
級 小格的外殼台詞 顯示 內容
1 「運算中……」 小格頭上轉圈圈 一句比喻（≤ 24 字）
2 「找到線索了！……大概。」 小格歪頭 一個提問：該注意哪一類現象、哪個檢視（≤ 30 字）
3 「好吧，直接說——啊不行，只能說這些。」 小格捂嘴 現在缺的是什麼性質（≤ 36 字），仍不給做法

  • 小格的笨拙是性格的一部分：它「想直接說」但被自己的規則擋住（L3 外殼），讓抽象提示有劇情理由。
  • 0 級即時回饋（規格 C9「看得見，卻碰不到」）也由小格說：「看得到，但搆不到喔。換個檢視試試？」

7. 文案風格指南與範例

7.1 規則

  • 讀者：國中到高中。句子短，一句只講一件事。
  • 每段旁白 / 便利貼 / 提示 ≤ 40 字；一句話劇情 ≤ 30 字。
  • 幽默來源：遊戲開發的日常（TODO、最終版、參數亂填、複製貼上）、社長的不靠譜、小格的吐槽。

4.1 世界狀態、步進、快照（core/types.ts、core/step.ts、core/snapshot.ts）

export type Mode = '3d' | '2d';
export type Visibility = 'both' | '2d' | '3d';
export type ObjId = string;
export type ItemId = string;                         // 'nib' | 'inkdrop' | 'seal' | 'diary:1' | 'scrap:4' …（content/items.ts 定義）
export type AbilityId = 'nib' | 'pin' | 'section' | 'mark';   // 規格 8 save.abilities
export type TextKey = string;
export type Json = null | boolean | number | string | Json[] | { [k: string]: Json };

export interface Player { x: number; y: number; z: number; vy: number; onGround: boolean; mode: Mode; z3d: number; facing: number }

/** 機制可擴充的世界狀態（各 mechanics 檔以 declaration merging 加欄位；值必須可 JSON 序列化） */
export interface WorldExt {}

export interface World {
  level: LevelDef;
  objs: ObjState[];                 // 關卡物件 + 執行期生成的實體（N7 定稿影子）
  derived: ObjState[];              // 每步由機制推導（N6 影子）；不進快照，restore 後重算
  byId: Map<ObjId, ObjState>;       // objs 與 derived 的索引
  player: Player;
  checkpoint: number;
  cleared: boolean;
  inv: Record<ItemId, number>;      // 取代 hasKey（N9）
  abilities: AbilityId[];           // 本關可用能力（4.9）
  flags: Record<string, true>;      // 進度旗標：'item:nib'、'on:plate'、'zone:hall' …（提示 / 謎題完成判定）
  ext: Partial<WorldExt>;
  msg: string; msgKey: TextKey; msgSeq: number;   // msg = 已解析字串（相容現有測試，見 7.3）
  events: GameEvent[];              // 本步事件外送匣，外殼每幀取走清空
  time: number;
  readonly rt: Runtime;             // 不序列化：機制表與文字解析器
}

衝突規則

掛點 合成方式 衝突處理
types / actions 唯一擁有者 重複 → compileMechanics 拋錯
visibility 第一個回傳非 undefined 者勝 目前只有 pin 使用；驗證器禁止同一物件同時 pinnable 與其他覆寫
presence AND 優先序寫在機制內（如 section 對 isPinned 放行 =「定稿 > 剖面」，規格 4-2c）
passable OR —
derive 串接 id 前綴必須是機制 id，重複 → 拋錯
canLand AND —
beforePhysics/afterPhysics/onModeSwitch 依陣列順序 plates 必須在 links 之前（index.ts 註解＋單元測試鎖定）

物件類型與機制的關係：類型由機制註冊（types 欄）；一個機制可擁有多個類型（links 擁有 gate/inkwall/inkbridge）；不屬任何行為的類型（floor、wall…）由 basics 註冊，讓驗證器能偵測「未註冊類型」。通用特性（solid、pushable、requires…）放在 ObjBase，任何類型可用；類型專屬參數放在 ObjKinds[type]。

機制間依賴：允許 mechanics 互相 import 查詢函式（例：section.ts import isPinned from pin.ts），必須無環（2.3 第 5 條）。不做事件匯流排；跨機制只有兩條通道：查詢函式、materialize。
