1. 設計支柱、目標玩家、時長

1.1 設計支柱（可用來否決提案）

# 支柱 檢查方式
P1 兩種視角缺一不可：每個謎題都必須同時用到 3D 與 2D 能力，只用一種視角必定解不開 每個謎題至少一條「只用單一模式」的反例測試
P2 一章一個頓悟：每章的核心 aha 推翻或延伸前一章建立的直覺（不是換座標） 第 5 節表格「本章 aha」欄不得重複
P3 以安靜推理為主：無真實計時、無精準跳躍要求；少數段落允許驚嚇（每章 ≤ 1 次）與追逐（全遊戲 3 次，N19），不構成失敗、不懲罰進度：被追上只回檢查點、進度與物件位置不丟；設定「減弱緊張效果」可讓追逐自動通過、驚嚇改平靜版（9.1） 不出現計時器；跳躍高度餘裕 ≥ 0.15（D10）
P4 物件會說話：可互動 / 只在某視角存在 / 可蓋印 等狀態一律有形狀符號，不只靠顏色 第 7 節無障礙檢查表
P5 叔公的疊圖術：機制都以老宅與製圖語彙命名（鋼筆、火漆印章、建築剖面尺、圖釘；顯示名見 story-bible 對照表），劇情與機制同源；主題「換個角度看，就會懂」 新機制命名須通過此檢查

1.2 目標玩家

  • 高中（約 16～18 歲）；喜歡解謎與輕度懸疑（Portal、Monument Valley、Inside 一類氣氛），不要求平台跳躍技術。
  • 劇情：暑假最後的週末，你獨自進入怪叔公的山上老宅，用他的鋼筆把宅邸疊成藏寶圖尋寶（見 story-bible-v0.2.md）；鍵盤操作（WASD / Space / F·Q / E / T / R，見 puzzle.html）。

1.3 時長估計〔推論〕

3. 謎題設計原則（可檢查的規則）

# 規則 依據 怎麼檢查
D1 每個謎題最多一個新概念；新概念先在「無失敗風險」的小場景出現一次（教），下一題要求主動使用（測），再下一題換條件（變） 〔來源〕Portal 開發者評論：每個概念都刻意介紹與訓練；任天堂四段式（導入→發展→轉折→收束）〔來源，二手分析〕 第 6 節每題新概念 ≤ 1（同一關可依序教多個，如 1-1）
D2 每個謎題必須同時用到 2D 與 3D（支柱 P1） 本作核心 每題至少兩條反例測試：只用 3D、只用 2D
D3 頓悟必須推翻一個合理的錯誤假設；在謎題說明中寫出「玩家最可能的錯誤嘗試」 〔來源〕Blow：刪掉沒有驚喜或彼此重疊的謎題；〔推論〕把錯誤嘗試寫進規格才能確認驚喜存在 第 6 節每題有「錯誤嘗試」欄
D4 不得有跳過關鍵步驟的捷徑，以邏輯層測試證明（取樣木箱位置 × 切換點的反例迴圈，比照玄關 for z of [...] 寫法） 現有測試慣例 C17 每關反例測試至少覆蓋「關鍵物件在別處」的取樣
D5 不放純粹的紅鯡魚；允許「誘導性錯誤」——看起來可行、試了會學到東西（如玩家站壓板「太輕」） 〔查不到〕密室社群對紅鯡魚的系統性論述未找到可信來源；〔推論〕浪費時間的假線索會破壞玩家對謎題的信任，容易直接放棄 每個非必要物件需寫出它教了什麼或屬於哪個隱藏要素
D6 規則一致、不臨時例外：同外觀 = 同規則（Blow 讓所有不受倒帶影響的物件都發綠光）；新規則用新外觀 〔來源〕Blow IndieCade 報導 機制庫每項都有專屬外觀符號
D7 提示只用場景字條，適量、抽象、不破題（意象 → 觀察問題 → 缺口的形狀；每題 0～3 張依預算，7.1.3），不給動作、不點名物件、不給數字、不點出 aha 依賴的性質（量表 7.1.1，H10）；同一級字條被超過 50% 玩家需要 → 謎題要重做；解答手稿被 ≥ 20% 打開 → 重做 〔來源〕Room Escape Artist 的提示文章 本機統計（第 8 節 puzzle:stats）＋ 驗證器（7.1.1）
D8 錯誤可逆：任何狀態都能以 T（木箱歸位）、R（重來）或回檢查點復原；不可能進入無解狀態而不自知 現有 C12、C13 每個新機制需寫「死局如何復原」
D9 整合章只允許用已教過的機制；筆桿機制（第四次升級）在地下室末段 4-3 教、閣樓首關 5-1 測試 / 變奏，之後 Boss 與終章才整合使用 〔來源〕Braid / The Witness 先把元素教完，之後難題只在探索已知機制的後果（Blow 相關報導） 第 5 節第五章「新概念」欄為「—」；6.9 教學順序自檢
D10 不靠精準操作：所有跳躍至少留 0.15 高度餘裕、0.3 水平餘裕；互動一律站穩 支柱 P3、現有 C9 數值寫進關卡註解並有測試

衝突規則

掛點 合成方式 衝突處理
types / actions 唯一擁有者 重複 → compileMechanics 拋錯
visibility 第一個回傳非 undefined 者勝 目前只有 pin 使用；驗證器禁止同一物件同時 pinnable 與其他覆寫
presence AND 優先序寫在機制內（如 section 對 isPinned 放行 =「定稿 > 剖面」，規格 4-2c）
passable OR —
derive 串接 id 前綴必須是機制 id，重複 → 拋錯
canLand AND —
beforePhysics/afterPhysics/onModeSwitch 依陣列順序 plates 必須在 links 之前（index.ts 註解＋單元測試鎖定）

物件類型與機制的關係：類型由機制註冊（types 欄）；一個機制可擁有多個類型（links 擁有 gate/inkwall/inkbridge）；不屬任何行為的類型（floor、wall…）由 basics 註冊，讓驗證器能偵測「未註冊類型」。通用特性（solid、pushable、requires…）放在 ObjBase，任何類型可用；類型專屬參數放在 ObjKinds[type]。

機制間依賴：允許 mechanics 互相 import 查詢函式（例：section.ts import isPinned from pin.ts），必須無環（2.3 第 5 條）。不做事件匯流排；跨機制只有兩條通道：查詢函式、materialize。
